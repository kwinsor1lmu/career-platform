# Exercise 05: Investigate a DNS or TLS failure

## 1. Setting and prediction

This investigation uses the supplied simulation, not my real domain. I expect `site.lab.example` to point to Railway and load successfully over HTTPS. I predict the failure is caused by an outdated DNS record pointing to the old server.

## 2. Failed check and evidence

Date: October 12, 2026. These results are simulated, not personally run.

```text
$ dig site.lab.example A +noall +answer
site.lab.example.  300  IN  A  198.51.100.24

$ curl -Iv https://site.lab.example/
* Connected to site.lab.example (198.51.100.24) port 443
* Server certificate: subject: CN=old-vm.lab.example
* SSL: certificate subject name does not match target host name 'site.lab.example'
curl: (60) SSL certificate problem: certificate subject name does not match target host name
```

DNS points to the old server, whose certificate does not match the requested hostname.

## 3. Diagnosis

The incorrect A record sends traffic to the old server. Its TLS certificate is for `old-vm.lab.example`, causing HTTPS verification to fail. The Railway application itself was confirmed to work through its provided URL.

What's uncertain is whether the custom domain and the TLS were correct before the DNS change.

## 4. Repair and repeated check

I would replace the old A record with a CNAME pointing to `current-app.up.railway.app`.

The supplied follow-up shows the updated DNS answer:

```text
$ dig site.lab.example A +noall +answer
site.lab.example.  300  IN  CNAME  current-app.up.railway.app.
current-app.up.railway.app.  300  IN  A  203.0.113.44
```

The repeated HTTPS check shows:

```text
$ curl -Iv https://site.lab.example/
* Connected to site.lab.example (203.0.113.44) port 443
* Server certificate: subject: CN=site.lab.example
* SSL certificate verify ok.
< HTTP/2 200
```

| | Before | After |
|---|---|---|
| DNS answer | `A 198.51.100.24` | `CNAME current-app.up.railway.app.` → `A 203.0.113.44` |
| Connected to | `198.51.100.24` | `203.0.113.44` |
| Certificate subject | `CN=old-vm.lab.example` (mismatch) | `CN=site.lab.example` (verify ok) |
| HTTP result | none (curl exit 60) | `HTTP/2 200` |

The IP address and certificate name changed, and HTTPS now succeeds. This supports my initial idea. These are supplied simulated results.

The DNS issue was the fault that came first.

## 5. What you learned

I could use `curl --resolve` to test the expected IP while preserving the hostname for TLS verification. If that succeeds but the normal request fails, DNS is probably the problem. If TLS succeeds but the page returns an application error, I would investigate the application instead.
